What The Tool Knows, And How It Knows It
Measured, the sensors

Packets, system logs, processes, port scans, presence sweeps. Things this machine watched happen.

Strongest evidence here. It is also the narrowest: a sensor on this host cannot see traffic between two other devices.

Looked up, the research worker

Asks public databases what an address, domain, CVE, hardware prefix or Windows binary is. Runs in the background, never blocks the chat.

Second-hand and dated. Every answer keeps its source and expires, so a stale fact gets re-checked instead of believed forever.

Worked out, the model

The conclusion drawn from the two above. Useful, and the weakest of the three.

Nothing outside this tool backs it. Marked as such so a later session treats it as a starting point rather than a settled fact.

Every answer says which of the three it came from. That is the whole point of the colours. A finding built on a measurement and a finding built on a guess should never look the same.

Three things the model is told to never over-read: an abuse score is how many strangers complained, not a verdict. proxy and datacentre say what an address is, not whether it is a problem. A binary being listed as abusable does not mean this copy did anything.

Nothing looked up can approve an action. Blocking a port, killing a process or quarantining a file still stops and asks you.

Activity Timeline
One list, in time order, of everything this app recorded. Findings, events, port scans, packet threats and device sightings are all stored in separate tables with their own timestamps, and this is the only screen that interleaves them.

What it is for: answering "what else was happening at the same time". A single alert on its own rarely says much. An alert with a new device appearing four minutes earlier, or a scan you ran yourself two minutes before, usually explains itself. That ordering is the whole value here, so read the rows above and below the one you came for.

Why the list is spread across the window rather than the newest rows. A capture running on this machine writes tens of packets a second; findings and log events arrive far more slowly. Taking the newest rows of all three together would fill the whole screen with packets from the last few seconds and push every finding off the end, which is what this page used to do. The window is therefore cut into equal time slices and each slice keeps its own share, so a finding and the traffic from its own moment appear together. The line above the list says how much of the window is not shown.

What it cannot tell you: it shows what was WRITTEN DOWN, not what happened. A quiet hour here can mean a quiet network or a sensor that was not running, and this page cannot tell those apart. Check the Dashboard tiles for what was actually collecting before reading a gap as calm.

Router View
What the router says is on the network, rather than what this machine could reach. A scan records whoever answered a ping inside a fraction of a second, so a device that ignores ping or was asleep reads as absent when it is simply quiet. The router exchanged the traffic itself, so it does not have that problem.

It is not a lease list and it is not traffic. This is the router's neighbour table: a device with a static address that is talking appears, a device holding a lease that is not talking does not, and entries age out after minutes to hours. So being listed means recent contact, and not being listed means nothing at all. Enrollment
There is no MDM behind this tool, so you are the authority on what belongs here. Naming a device stops the agent re-guessing it every session. Marking one permanent is a stronger statement: it means the device is supposed to be present at all times, and it is what turns an absence into a question instead of a shrug.

The counts below are deliberately not added together. Only the first is a number of devices you should act on.

Only devices with a stable MAC address get listed here. That's why this tab can show fewer devices than the Network tab. The MAC address is what ties a row to one physical device over time, and some devices don't give us one we can trust:
  • Randomized MAC: most phones, tablets and newer laptops make up a new private address per network, and some rotate it every so often. So one phone can turn up as two or three rows, and marking it permanent wouldn't stick, since next week it shows up as a "new" device. These are counted in the transient tile below, not listed. If you want your own phone listed, turn off "private Wi-Fi address" (or "random hardware address") for this network on the phone and rescan.
  • No MAC: ARP had no entry for it, or it sits behind another router one hop away, where MAC addresses never reach us. Nothing to identify it by, so it goes in the no address tile.
  • Unreadable MAC: something is on record but it isn't a MAC we can read (cut off or junk). We don't guess, so it's not listed. A fresh scan usually fixes it.
  • Retired: devices marked as gone for good. They stay out of this list and stop raising absence alerts.
All of these still show on the Network tab, where the Identity column says which group each row is in.

One device, several addresses
known_devices is keyed on IP, so a phone that took three DHCP leases is three rows and three entries in the review queue. Merging says these are the same thing, and the extra rows stop being asked about.

Only you can do this, and that is on purpose. Merging removes a row from the review queue without touching any suppression counter, so an agent that could merge could fold an unexplained device into the printer's identity and it would simply stop being a question. Nothing in the suppression audit would show it. That is blinding done by filing, and it is why there is no tool for this at any privilege level.

Merge into the address you think of as the real device. It is reversible, and unmerging puts the row straight back in the queue.

Running Processes
Everything running on this machine, read from the kernel's own process table. The logic behind each colour is as follows: first, what the package records say about the executable; second, where it lives; third, whether anything has already been raised against that process.

On this platform the file check is against your package manager. Each executable is compared with the digest the package that owns it recorded when it was installed, so green means this is still the file this machine shipped. It does not mean the program is behaving. A file no package owns is amber: ordinary for anything built by hand, and worth a look if it is running from a temporary folder.

Nothing here is hashed when the tab opens. The comparison above is a fast digest over small system binaries, cached; press inspect on a row for the full sha256, the owning package, and whether that exact binary is known to anyone.

green means the file matches the package that installed it, not that the behaviour is fine: signed software gets abused every day. amber is a reason to look, not a finding: unowned binaries and temp folders are both ordinary. faint grey is a kernel thread: part of the kernel, with no file of its own and nothing to check. grey means nothing could be read about it, which is not the same as safe.

Port Scan Results
This scanner now does TCP and UDP. Every host gets a TCP connect pass over the port set you chose, and a UDP pass over a fixed list of real UDP services with a proper request for each one: DNS, NTP, SNMP, NetBIOS name service, SSDP, mDNS and LLMNR. Rows are tagged port/tcp or port/udp so a result always says which question was asked.

UDP has three answers and only one of them is "open". A row here means the port replied. An ICMP unreachable means nothing is listening. Silence means neither: the service may be listening and quiet, or filtered, or it wanted a payload we did not send. Silent UDP ports are listed under the scan result as udp_no_answer and are never shown as closed. A port outside the UDP list was not asked about over UDP at all, and a full UDP sweep is deliberately not offered: it is hours per host for answers that would almost all be silence. Open TCP ports found on the hosts you scan. Every scan is recorded, so a port that stays open is observed many times; those repeats are collapsed into one row here, with the sighting count beside the timestamp. Nothing is deleted, tick every scan to see each observation on its own line. Ports touched by the scan you just ran flash amber for ten seconds, tagged NEW if this host has never shown that port before, or CONFIRMED if it was already known. Scope decides what a result means: self-scan ran from this machine on itself, which proves a service is listening but says nothing about who can reach it; remote ran across the network and does measure reachability. Scanning a host outside your own network asks for approval first.

Behavioral Baselines
How this works, in plain words. Every address, process, port and user is watched session after session, and the tool writes down what it usually does: how much, how often, at what hours, and to where. That record is its normal. Confidence grows with the number of separate sessions it has been seen in (2 sessions is low, 4 is medium, 6 is high), never with how many times it was polled in one sitting. When something later behaves far outside its own normal, it lands in Recent Deviations below: about 2 steps away from usual is worth a note, 3 or more is an alert. Unusual is not the same as bad; it is a reason to look. And silence is never approval: an alert nobody answered stays unreviewed, it does not become normal.

What the agent did while nobody was asking
The duty loop
It wakes on its own: emergency when a flood condition is seen, and at four regular moments a day, when it reports on up to two findings from different tools and goes back to sleep. Between those moments it looks at the clock every minute and does nothing, the line below counts those looks separately from wake-ups, so a quiet schedule cannot be mistaken for a loop that stopped. If it is not running, nothing is investigating anything and this page stays as empty as it is, which is why the line below is here rather than a green tick.

Integrity Journal
Every high-value write is hashed into a chain. Tampering with a finding, an event or a baseline breaks it, so this cannot prevent anything on a machine somebody else controls, it makes it detectable.

An unanchored chain proves less than it looks like it does. Verifying with no anchor only shows the chain is consistent with itself, and a chain rebuilt from scratch by whoever rewrote the data is also consistent with itself. Take an anchor, then copy the hash somewhere this machine cannot reach: your phone, a password manager, another host. An anchor sitting on the same disk as the database catches accidents, not attackers.
Database Size
The packet record is nearly all of this file and it grows for as long as the app runs. When it passes the budget, the oldest whole capture runs are deleted at the next clean shutdown, oldest first, never part of a run.

The behavioural baselines are never pruned. What a prune costs you is the raw evidence behind a measurement, not the measurement.

There is no prune button here, deliberately. Deletion is the only thing in this application that cannot be undone, so it does not get a one-click home on the same page as everything else. To prune now, stop the app and run python scripts/prune_db.py, which shows you the plan before it touches anything.
Ports You Have Said Are Normal
Naming a device says nothing about which of its ports belong to it, so an identified device can keep raising the same open-port finding session after session. This is where you answer that once, for one port on one device.

Declaring clears the findings already raised for that port on that device, and stops new scans raising more. Everything else keeps raising: any other port on the same device, this port on any other device, the device going missing or changing hardware, and everything behavioural.

The model cannot do this. There is no tool for it and there is not going to be one, because a model that can mark its own findings expected has a path to silencing itself.

Stop the app
Same clean stop as Ctrl+C in the terminal: final rollup, enrichment worker stopped, then retention.

This exists because the terminal is not always reachable. On 2026-09-08 a console window would not come back from minimised, and with Ctrl+C as the only door the machine had to be shut down instead, so the rollup and retention never ran. The app was healthy the whole time and was still serving this page. So this is the second door.

Retention on a large database takes minutes. The app is gone when this page stops answering, not when the button greys out.
What is on, what is off, and why
A fresh install shows a dashboard of zeros, and zeros look like a clean network. Every collector already writes a reason for a human when it cannot run. This is the place they are all written down together.

Green is running. Amber is switched off or unconfigured, which is not a fault, most of these are optional and off by default. Red is something that is supposed to be working and is not.

Most of this is the verdict of somebody else's last check, not a live test. Each collector polls on its own timer, so after you fix the far end of one, give it a poll cycle before believing the colour. Refresh re-reads the page; it does not re-run anyone's poll.
